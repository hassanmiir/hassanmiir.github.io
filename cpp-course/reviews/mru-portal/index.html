The Project at a Glance

One C++ server, one web page

A complete, self-contained university portal demo — no framework, no build system beyond a compiler.

Backend — server.cpp

Boost.Beast HTTP server + SQLite. Login, state, assignments, grading, schedule, attendance and file uploads. ~670 lines.

Frontend — index.html

Single-page app (HTML + JS in one file). Teacher and student dashboards, served by the same server.

Storage — portal.db

SQLite with 5 tables (tasks, materials, submissions, schedule, attendance) + an uploads/ folder.

Deploy — Dockerfile

Two-stage Debian build, runs on Render via cloud-start.sh. Reads PORT / MRU_DATA_DIR.

What's Done Well

Genuinely solid engineering

Server-side auth

Role is decided from the demo account, never trusted from the browser. Textbook-correct.

Safe SQL

Prepared statements with bound parameters everywhere — no string-concatenated SQL, no injection.

Atomic saves

Writes run inside BEGIN IMMEDIATE … COMMIT with rollback on error.

Careful uploads

4 MiB cap, extension allow-list, path-traversal checks, random stored filenames.

Access control

canDownload() gates every file; students only see their own submissions.

Real deployment

Clean Docker multi-stage build, env-driven host/port/data dir, graceful disconnect handling.

1 · Authenticate

POST /api/login validates the demo account, returns a Bearer token + role.

2 · Act

POST /api/grades → mutate("grade") checks role & range, updates memory.

3 · Persist

save() writes all tables in one transaction; readDb() rebuilds state.

The in-memory JSON mirrors SQLite so the browser API stays simple — a deliberate, well-documented trade-off.

Improvement 1 · Data & Multi-User

From one demo student to a real class

A

Real users instead of a hard-coded name

Today every submission is "Laurynas K." and there are two fixed accounts. Add a users table (id, email, hashed password, role) so many students and teachers can log in.

B

Update changed rows, not the whole database

save() deletes and re-inserts every table on each write. Switch to targeted UPDATE/INSERT/DELETE — the design the code's own comment recommends.

C

Model courses as data

Courses 1–6 and the validCourse(1..3) rule are hard-coded. A courses table with an owning teacher makes the portal configurable and matches the Course class in your diagram.

Improvement 2 · Security & Robustness

Hardening for real use

A

Persist & expire sessions

Tokens live in an in-memory map, so every restart logs everyone out and sessions never expire. Store them with an expiry, or use signed tokens.

B

Hash passwords

Demo passwords are compared as plain text. Even for a demo, store a salted hash (argon2 / bcrypt) and compare against that.

C

One connection per request → a small pool

A single global mutex serialises every request. A connection pool (or SQLite WAL readers) would let reads run concurrently under load.

D

Add rate limiting & HTTPS

Login has no throttling. Add basic rate limiting and serve behind TLS in deployment.

Improvement 3 · Features

Finish what the diagram promises

The UML models more than the demo currently exposes. These additions make the portal feel complete.

Attendance UI for students

Attendance is recorded and stored but hidden from students. Let each student see their own attendance record.

Grade overview & averages

Add a teacher view that lists all grades per course with an average — reuse the loops & conditionals from class.

Deadline awareness

Tasks have a due date but nothing uses it. Flag late submissions and show "due in N days".

Edit, not just add/remove

Assignments and materials can be created and deleted but not edited. Add an update action for each.

Notifications

Show students a badge when a new grade or assignment appears since their last visit.

Search & filter

Filter assignments by course or status — a natural place to practise SQL WHERE clauses.

Improvement 4 · Engineering Quality

Make it easier to grow

Split the one big file

Separate storage, auth, routing and handlers into their own files — easier to read, test and share in a team.

Add a README

The repo has no README. Document how to build, run, log in, and what each endpoint does.

Write a few tests

Even simple tests for decodeBase64, validCourse and grading bounds would catch regressions.

Use real C++ types

The diagram shows classes; the code uses JSON maps. Small structs (Task, Submission) would match the design and cut str()/num() lookups.

Together these turn a 670-line demo into a project a team can keep building on.
